# Transition 与 Deferred UI：区分紧急更新和可延迟更新

Transition 让某些更新以非阻塞方式在后台渲染；`useDeferredValue` 让一部分 UI 暂时继续使用旧值，同时 React 尝试用新值完成后台 render。

<MentalModel title="输入必须立即响应，昂贵结果可以稍后跟上">urgent update 负责输入框、按钮反馈等直接交互；transition/deferred work 负责允许稍后提交的非紧急 UI。它们不会让计算消失，而是改变调度与呈现优先级。</MentalModel>

<Observation>Transition 不适合控制文本输入本身；输入的 State 应同步更新。`useDeferredValue` 也不是 debounce：它没有固定毫秒延迟，而是与 React 渲染调度协作。`startTransition` 的 callback 会立即执行，非阻塞/可中断的是被标记更新对应的渲染工作，而不是 callback 像定时器一样延后执行。</Observation>

<AntiPattern title="把所有更新都包进 startTransition">非紧急只是 UX 语义，不是“性能优化开关”。错误标记会延迟本应立即反馈的界面。</AntiPattern>

<Boundary title="机制事实 ≠ 当前 Demo 的直接证据">
React 19.2 的 `useDeferredValue` 后台 render 在机制上可以被更紧急更新打断并重新开始；但当前 Demo 没有记录 render attempt/abandon，因此只能直接观察旧值继续显示、`stale` 状态与最终提交结果，不能声称已经定位到某一次后台 render 被中断。网络请求的频率控制也仍可能需要 debounce/throttle/cache；Transition/Deferred 不替代请求层策略。
</Boundary>

<Boundary title="为什么昂贵结果组件使用 memo">
Deferred 模式下，父组件的 urgent render 仍会发生。把昂贵结果子树用 `memo` 隔离后，当它收到的 `resultQuery` 仍是旧值时可以跳过重复工作；随后 React 再用新的 deferred value 尝试后台 render。否则父 render 自身仍可能重新执行昂贵子树，掩盖 deferred value 想表达的调度边界。
</Boundary>

<Summary>
- urgent UI 保持即时；Transition 标记非紧急更新。
- `useDeferredValue` 让消费者暂时使用旧值，并可显式标记 stale。
- Direct/Deferred 对照能观察呈现差异，但当前 Demo 不声称捕获 React 内部被丢弃的 render attempt。
- Transition/Deferred 都不是 debounce，也不会自动减少请求或计算总量。
</Summary>
