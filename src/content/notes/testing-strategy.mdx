# Testing Strategy：测试用户可观察行为，而不是实现细节

<MentalModel title="测试是一组不同反馈速度的证据">
单元/组件测试快速验证局部行为，集成测试验证多个边界协作，E2E 从浏览器入口验证关键用户路径。目标不是让每一层重复同一断言，而是用最低成本覆盖最重要的失败模式。
</MentalModel>

<Experiment title="从实现断言改成行为断言">
查看中间 Demo 给出的测试样例：优先通过 role、accessible name 和用户事件操作 UI；再对比直接查询 class、内部 state 或组件实例的写法。思考重构实现但保持行为时，哪类测试更稳定。
</Experiment>

<Observation>
React Testing Library 的核心价值不是“更方便 query DOM”，而是推动测试靠近用户使用方式。`getByRole` 往往同时验证语义和可访问名称，因此比 class selector 更有产品意义。
</Observation>

<Compare>
### Vitest + RTL
反馈快，适合组件状态、事件、条件 UI 与局部集成；通常运行在模拟 DOM 环境。

### Playwright
真实浏览器，适合导航、焦点、布局、网络、history、跨页面关键路径；成本更高，应聚焦高价值流程。
</Compare>

<AntiPattern title="测试内部 state 或实现调用次数">
除非调用协议本身就是公共契约，否则测试内部 hook/state、私有函数或脆弱 DOM 层级会让安全重构变得困难。优先断言用户能看到/操作的结果。
</AntiPattern>

<Boundary title="测试通过不等于产品正确">
自动化只能证明已编码的断言。可访问性、视觉回归、真实网络故障、浏览器差异仍需要相应工具与人工验收。TypeScript 也只能证明静态类型关系，不能替代运行时行为测试。
</Boundary>

<Summary>
- 从风险和用户行为设计测试，而不是从函数列表设计测试。
- RTL 优先语义 query + user-event。
- E2E 留给真实浏览器边界和关键路径。
- 各层避免重复，CI 证据要能定位失败责任。
</Summary>
