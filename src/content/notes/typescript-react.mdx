# TypeScript for React：让类型描述边界，让运行时负责行为

这节课不把浏览器 Demo 伪装成 TypeScript 编译器。中间 Demo 负责展示 **React 运行时行为和组件 contract 的含义**；Source 面板里的 `.tsx` 文件负责展示真实类型写法；真正的“这个错误会不会被 TypeScript 拒绝”必须交给 `tsc` / CI。

<MentalModel title="类型系统检查关系，React 运行时执行行为">
TypeScript 能在开发期检查 props、children、事件、ref、状态变体和泛型之间的关系，但它不会改变 React 的 render/commit 语义，也不会在浏览器里替你验证 API、localStorage、URL 或用户输入。先设计可信的组件协议，再用类型系统证明其中能静态证明的部分。
</MentalModel>

## 先分清三层

- **Demo**：观察受控输入、State 更新、ref 聚焦等真实 React 行为；这里运行的是 JSX/JavaScript，不产生 TypeScript diagnostics。
- **Source**：阅读 `react-boundaries.tsx` 与 `generic-patterns.tsx`，观察 props、`ReactNode` / `ReactElement`、事件、nullable DOM ref、discriminated union、controlled contract 和泛型关系如何写进类型。
- **CI / typecheck**：验证 `@ts-expect-error` 标记的非法调用确实会报错，同时合法样例持续通过编译。当前仓库的共享 typecheck 脚本由基础设施任务接入，本节不假装浏览器已经完成这项验证。

## Props 与 children：只声明真正需要的能力

公共组件应暴露最小、稳定的 props contract。普通可渲染 children 通常使用 `ReactNode`；只有 API 真正要求“一个 React element 对象”时才收窄到 `ReactElement`。不要把 `JSX.Element` 当成所有业务组件 API 的默认返回/children 类型，也不要依赖 TypeScript 去限制“只能传某一种 JSX 标签”——React 官方文档明确指出这种 JSX 子元素种类约束并不能可靠由 TypeScript 表达。

## Event：让元素类型保留在 currentTarget 上

JSX 内联 handler 往往可以直接推导事件类型；抽出 handler 时，再显式写 `ChangeEvent<HTMLInputElement>`、`FormEvent<HTMLFormElement>` 等具体类型。关键不是记住类型名，而是保留“事件来自哪个元素”的关系，这样 `event.currentTarget.value` 等属性才有可靠类型。

## State：让非法状态难以表达

```ts
// 容易产生矛盾组合
{ loading?: boolean; data?: User[]; error?: Error }

// 合法状态被编码进类型
{ status: 'loading' }
| { status: 'success'; data: User[] }
| { status: 'error'; error: Error }
```

Discriminated union 的价值不是“更高级”，而是缩小合法状态空间。若一个状态组合在业务上不应该存在，就尽量不要让它轻易通过类型系统。

## Ref：具体 DOM target + nullable 生命周期

DOM ref 应指向实际元素类型，例如 `HTMLInputElement`。首次 render 时 DOM 尚未 commit，ref 可能为 `null`；因此 `HTMLInputElement | null` 与可选访问不是噪声，而是在描述真实生命周期边界。ref 仍然是 escape hatch，类型正确不代表应该用 ref 取代 props/state 数据流。

## Controlled contract：value 是事实，callback 是请求

对于受控组件，类型可以把 `value` 与 `onValueChange` 一起设为必需，防止调用方只给一半 contract。但类型只能保证“callback 存在且参数类型正确”，不能保证父组件一定接受请求、更新 value，也不能保证业务权限正确；这些属于运行时/业务语义。

## Generic：只保留真实的输入输出关系

`SelectList<T>` 的价值在于 `items: T[]`、`renderItem(item: T)`、`onSelect(item: T)` 共享同一个 `T`。`useHistory<T>` 的价值在于 initial/current/update/history 保持同一类型关系。若泛型参数没有连接两个以上真正相关的位置，通常不值得引入。

<AntiPattern title="为了消除红线使用 any / as">
`as` 不会做运行时验证，`any` 会切断类型关系。API、localStorage、URL、用户输入等 trust boundary 应先做运行时解析/校验，再进入可信的 TypeScript domain；不要把断言当成验证。
</AntiPattern>

<Boundary title="静态保证有明确边界">
TypeScript 类型在编译后被擦除。它可以证明“调用代码是否满足声明的类型 contract”，但不能证明服务端响应一定诚实、DOM 一定存在、React 组件一定按业务预期更新，也不能替代交互测试。静态检查、运行时校验和 React 行为测试解决的是不同问题。
</Boundary>

## 项目决策规则

- 局部值能安全推导：**让 TypeScript 推导**，不要为“覆盖率”重复注解。
- 公共组件输入/输出：**明确 props contract**，只暴露真正需要的字段。
- 多个 boolean/optional 字段存在矛盾组合：考虑 **discriminated union**。
- 抽出的 DOM event handler：保留具体元素事件类型，优先围绕 `currentTarget` 建模。
- DOM ref：使用具体元素 + `null` 生命周期边界。
- 一组 API 需要保持调用方类型关系：使用 generic；否则先不要泛型化。
- 外部不可信数据：先 runtime validate，再进入静态类型域。
- 要证明错误示例“确实报错”：交给 `tsc`/CI，而不是浏览器 Demo。

<Summary>
- Demo 证明 React 运行时行为；Source 展示类型 contract；CI 才负责真正 typecheck。
- `ReactNode` 是常见 children 边界，`ReactElement` 只在确实需要 element 对象时收窄。
- union、具体 event/ref 类型和 controlled props 的目标都是保留真实关系并减少非法状态。
- 泛型只在需要保存输入输出关系时使用。
- TypeScript 不替代运行时校验，也不替代 React 行为测试。
</Summary>
