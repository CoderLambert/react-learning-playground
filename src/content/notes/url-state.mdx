# URL State：让页面状态可寻址

<MentalModel title="URL 是页面级共享状态，不是普通组件 state">
当状态决定“用户正在看哪个资源、筛选条件是什么、当前页是哪一页”时，它通常需要被刷新恢复、复制分享、前进后退重放。此时 URL 是比 `useState` 更合适的所有者；组件 state 负责短生命周期交互，Router 负责把 URL 与页面状态同步。
</MentalModel>

<Observation>
URL state 的价值不只是“刷新不丢”。它同时定义了页面的外部协议：书签、分享、搜索引擎、分析系统和测试都可以通过稳定 URL 指向同一语义状态。
</Observation>

<Compare>
### Local state
适合 modal 是否打开、输入框草稿、hover 等临时 UI；不要求可分享。

### URL state
适合资源 id、tab、筛选、排序、分页等页面语义；应能序列化并有明确默认值。

### Server state
数据实体本身通常由请求缓存层管理；URL 只保存“查询什么”，不要复制整个响应。
</Compare>

<AntiPattern title="URL 和 useState 各存一份同义状态">
如果 `searchParams` 有 `page=3`，组件又维护 `const [page, setPage] = useState(3)`，就产生两个 source of truth。刷新、外部导航或 Back/Forward 很容易让两者漂移。优先从 Router 状态派生当前值。
</AntiPattern>

<Boundary title="React Core 不负责路由">
React 提供组件、state 与并发渲染语义，但 History API、路由匹配、search 参数解析、导航 pending 状态通常由 Router/Framework 负责。不要把某个 Router 的 loader/search API 当成 React Core API。
</Boundary>

<Summary>
- 页面级、可分享、可恢复的状态优先进入 URL。
- URL 应是该语义的单一数据源，而不是组件 state 的备份。
- Router 负责 location 与导航；React 负责根据当前输入渲染 UI。
- URL 保存查询意图，不应复制 server-state 响应。
</Summary>
