# Navigation Boundary：把“跳转”当成一次状态转换

<MentalModel title="导航不是 click 后立即换 DOM">
客户端路由中的导航是一段异步状态转换：发起 intent、计算目标匹配、可能加载代码和数据、处理 redirect/error，最后 commit 新页面。用户在这段时间仍需要明确反馈，并且旧页面是否继续可交互要由产品语义决定。
</MentalModel>

<Experiment title="区分导航 pending 与普通组件 loading">
触发中间 Demo 的慢导航，观察旧页面、导航指示器和最终页面。连续触发不同目标，判断 pending 状态属于哪次 navigation，而不是把所有异步工作都塞进全局 `isLoading`。
</Experiment>

<DemoReference action="触发慢导航并观察 pending/完成边界" observe="确认用户在导航期间知道系统正在做什么，且最终 URL 与页面一致。" />

<Observation>
导航 pending 是 Router 对“当前 location → 下一 location”的状态描述。它和某个组件内部 fetch 的 loading 不同：导航可能同时影响 URL、匹配树、数据请求、滚动恢复与历史记录。
</Observation>

<AntiPattern title="每次导航都清空整屏">
无条件用全屏 spinner 替换已有页面会制造布局闪烁，也丢失用户上下文。更好的策略通常是保留稳定 shell，在真正变化的 route boundary 显示 pending；是否阻塞交互取决于业务一致性要求。
</AntiPattern>

<Boundary title="Transition 与 Router navigation 不等价">
React 的 `startTransition`/`useTransition`提供非阻塞更新优先级语义；Router 可以利用 React 并发能力，但导航状态、redirect、history 与 route data 仍由 Router/Framework 定义。不要用一个 `useTransition` 自制完整 Router 状态机。
</Boundary>

<Summary>
- 把导航理解为异步状态转换，而非瞬时页面替换。
- pending UI 应贴近真正变化的 route boundary。
- URL、history、redirect 和 route data 属于 Router 责任。
- React Transition 是渲染调度工具，不是导航协议。
</Summary>
