# Review: 条件渲染与业务四态

## Verdict

Note 的主线“先建模状态，再映射 UI”是正确的，四态切换实验也真实可执行；但 Demo 对 empty state 的两处说明互相冲突，容易让学习者误以为“空态必须单独存 state”。

## Hard gates

- **Gate A — Correctness: PARTIAL**。React 条件渲染确实使用普通 JavaScript 控制流；`0 && <View />` 可能渲染 `0` 的边界也准确。问题在 Demo：Empty 分支写着“空态是独立业务状态，不应该伪装成成功但数组长度为 0 的隐式分支”，但页面末尾又正确建议 `isEmpty` 能从 `items.length` 推导时不要额外保存 State。两句不能同时作为通用规则。
- **Gate B — Demo Contract: PASS**。四种 status、early return、ternary、`&&` 开关都能实际操作和观察。
- **Gate C — Mental Model: PARTIAL**。分支映射模型清楚，但 empty 的“业务语义”和“state 存储方式”被混为一谈。

## Important gaps / boundaries

1. 应区分“Empty 是值得显式设计的 UI 状态”与“必须拥有独立 `empty` state”。例如请求成功且 `items.length === 0` 时，可以从 `{status: 'success', items: []}` 派生 Empty UI；若后端协议本身区分 `empty` 结果，单独 status 也合理。
2. `loading/error/empty/success` 是否互斥取决于产品模型。后台刷新时可以同时拥有“已有成功数据 + 正在 refetch”，因此四态并不是所有请求 UI 的通用状态机。
3. `&&` 边界可再指出：React 不渲染 `false/null/undefined`，但数字 `0` 是可渲染节点，所以左操作数类型才是关键。
4. “复杂场景优先 discriminated union”在 TypeScript 中尤其有价值，但本章是 JSX/状态建模基础，可以表述成单一 `status`/有限状态模型，避免提前依赖 TS 概念。

## Clarity / engineering usefulness

整体结构自然，Demo 的语法对照有价值。最需要修的是 Empty 文案，而不是增加更多教学卡片。

## Recommended changes

- 把 Demo Empty 文案改成：**Empty 是独立的 UI 语义，但不一定是独立存储的 State；若可由成功数据为空推导，就直接派生。**
- 在 Note Boundary 增加“后台刷新/已有数据”等可并存状态反例，防止把四态模型绝对化。
- production decision rule：**先定义业务状态是否互斥，再决定用单一 status、派生布尔值还是多个正交状态；条件渲染只消费模型，不负责制造第二份状态。**
