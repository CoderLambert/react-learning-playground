# use-reduce-with-context.mdx 审核记录

## 当前结论

**核心方向正确，但原 Demo 含 purity bug 和误导性性能绝对表述。** Gate A：PASS after Demo fix；Gate B：PARTIAL；Gate C：PASS。

## Correctness / React 19.2

- `useReducer` 返回的 `dispatch` identity 是稳定的。
- Context consumer 是否因 Context 更新而重新 render，取决于它是否读取了发生 value identity 变化的 Context；拆 State / Dispatch Context 可以让 dispatch-only 组件不订阅 State Context。
- 这不等于 dispatch-only 组件“绝对不会重渲染”。它仍可能因为自身 state、props、其他 Context、父级重新创建的元素路径或其他 React 更新来源而 render。
- 本轮已修复 `taskReducer` 内部调用 `Date.now()` 生成 ID 的 purity 问题：ID 改为事件处理阶段生成并通过 action 传入。

## Mental model

Note 的“Reducer 管转换、Context 管跨层分发、读写可分开订阅”是有效模型。建议把优化描述稳定在 **subscription boundary**，而不是“彻底隔离”“0 无效重渲染”。这能让学习者区分 React 的 Context 通知机制与更广义的 render 原因。

## Demo ↔ Note

Demo 现在真实记录两个组件的 render 次数，可以用于比较当前树结构下的现象；但 Note 不应把一次实验结果升级为全局保证。

还缺一个真正的“单 Context”可执行对照。当前页面只显示单 Context 的静态代码片段，实际交互区只运行双 Context 版本，因此 Experiment 中“比较单 Context 与双 Context”的契约尚未完全成立。

## 缺失边界 / 反例

- 拆分 Context 的直接收益是避免 dispatch-only consumer 订阅 state value；它并不提供 selector，也不会自动优化仍读取 State Context 的组件。
- 单 Context 在小模块、低频更新或简单 API 中可能更清楚；没有测量证据时不应以“工业级标准实践”强制双 Context。
- 若需要字段级订阅、复杂 devtools 或跨模块 store 组织，应重新评估外部 store，而不是无限拆 Context。

## 清晰度与工程决策

本轮已将 Demo 中“绝对不会”“永久 0 重渲染”“性能杀手”“工业级标准”等营销式绝对措辞收紧，并改用 React 19 的 `<Context value={...}>` Provider 写法。

项目决策规则建议写成：**当读 state 与只发 action 的消费者明显分离，并且订阅范围确实影响可读性或性能时，拆 State/Dispatch Context；否则优先保持简单。**

## 建议修改

1. 若 Note 保留“比较单 Context 与双 Context”，给 Demo 增加真实可切换/并排的单 Context 实验；否则把 Experiment 改为只观察双 Context 的订阅边界。
2. 明确 render counter 是当前 Demo 树结构的实验结果，不是 React 对所有父级路径的保证。
3. 保留 dispatch stable identity，但删除“永远不渲染/无需 memo”类绝对结论。
4. 强调双 Context 优化的是订阅面，不是 reducer 本身的魔法。
