# effect-event 审核建议

## 当前结论

- Gate A Correctness：**PASS**
- Gate B Demo Contract：**PASS**
- Gate C Mental Model：**PASS**

## 当前 verdict

本课现在把 Event / Effect / Effect Event 的职责边界讲清楚，并且把原先只有文字描述的“错误依赖 vs Effect Event”改成了两个同时运行的真实 Effect。学习者可以直接操作同一组 `roomId` / `theme`，观察 setup 次数如何变化。

## 事实与 React 19.2 边界

- Effect Event 用于 Effect 逻辑中需要读取最新 committed props/state、但这些值不应成为重新同步条件的部分。
- Effect Event 只能从 Effect 或其他 Effect Event 调用，不应在 render、普通事件处理器中调用，也不应传给其他组件/Hook。
- 它不能用来隐藏真实依赖；真正决定外部同步关系的响应式值仍必须保留在 Effect dependencies 中。
- Effect Event 函数 identity 不是稳定性保证，不应被理解为 `useCallback` 替代物。

## Mental Model

学习者可以回答：为什么 theme 在“通知文案”里是最新值，却不必成为“连接生命周期”的重新同步条件；什么时候必须保留依赖；什么时候逻辑其实应该留在普通 Event Handler，而不是 Effect/Effect Event。

## Demo ↔ Note ↔ Source

当前对照是可执行的：

1. 左侧真实 Effect 依赖 `[roomId, theme]`；切 theme 会 cleanup + setup。
2. 右侧真实 Effect 只依赖 `[roomId]`，通知读取放在 `useEffectEvent` 中；切 theme 不重建连接。
3. 切 roomId 时，两侧都会重新 setup，因为 roomId 是真实同步条件。
4. setup counter 在 Effect setup 内更新，不再用事件 handler 预测 Effect 次数。
5. Note 明确要求比较同一次操作前后的计数增量，并解释 development Strict Mode 可能增加初始 setup → cleanup → setup，因此不把绝对初始数字当作生产语义。

Gate B 因此从 FAIL 更新为 PASS。

## 重要边界 / 反例

当前 Demo 使用定时器模拟连接成功事件，适合教学职责边界，但不等价于真实 WebSocket/第三方连接库。真实项目还应验证订阅 API 的 cleanup、重连策略和错误恢复。

另一个重要反例是：如果 `theme` 真正改变了连接协议、endpoint 或订阅参数，那么它就属于同步条件，不能为了“少重连”而藏入 Effect Event。

## 清晰度与生产决策

生产决策规则已经明确：先识别外部同步关系；把决定同步关系的值作为依赖；只有 Effect 已发生时需要读取的非响应式最新信息才考虑 Effect Event。不要从“我不想让 Effect 重跑”反推依赖数组。

## 建议修改

当前没有阻塞 Gate 的修改。后续若扩展课程，可增加真实事件订阅 API 的例子，但不应把 Effect Event 扩写成通用 memoization 或依赖逃逸工具。
