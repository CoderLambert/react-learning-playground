# transition-deferred 审核建议

- Gate A Correctness：PASS

## 当前 verdict

本课现在有可执行的 Direct vs Deferred 对照，并把“后台 render 可中断”从实验观察收窄为 React 19.2 的机制事实；当前 Demo 不再冒充能识别某一次被丢弃的 render attempt。

## 事实与版本边界

`useTransition` 把其中的 State update 标记为非阻塞 Transition；受控文本输入自身不能由 Transition 更新。`useDeferredValue` 让消费者先继续看到旧值，再尝试用新值做后台 render。该后台 render 在机制上可中断；如果新的 value 到来，React 可以重新开始后台工作。

需要保持两个边界：

- `startTransition` callback 本身会立即执行，非阻塞/可中断的是其中标记更新对应的渲染工作；它不是 `setTimeout`。
- `useDeferredValue` 没有固定毫秒延迟，也不会自动减少网络请求。

## Mental Model

“输入必须立即响应，昂贵结果可以稍后跟上”能够正确区分 urgent 与 non-urgent UX。学习者可以解释：什么时候控制更新源并使用 Transition；什么时候保留上游同步 state、只延迟下游消费；为什么这两者都不是 debounce。

## Demo ↔ Note ↔ Source

当前实验已经对齐：

1. 搜索区提供 Direct / Deferred 两种真实模式，使用同一个受控 `query` 和同一个昂贵结果组件。
2. Direct 模式下结果直接消费 `query`；Deferred 模式下结果消费 `deferredQuery`，并展示 `input`、`result query` 与 `stale`。
3. `ExpensiveResults` 使用 `memo`，避免父组件 urgent render 在 deferred value 尚未变化时无条件重做昂贵结果工作，更接近 React 官方推荐的 deferred-render 边界。
4. tab 区继续展示 urgent selection、Transition 中的 `visibleTab` 与 `isPending`。
5. Note 明确说明当前 Demo 没有 render-attempt/abandon instrumentation，因此不能把某次具体后台 render 标记为“已被中断”。

Gate B 因此从 FAIL 更新为 PASS。

## 重要边界 / 反例

如果昂贵工作本身可以通过数据结构、缓存、虚拟列表或拆分计算真正消除，应优先降低实际成本；Transition/Deferred 主要调整调度和呈现优先级，不是替代算法优化。

对于远程搜索，`useDeferredValue` 仍可能让每次输入触发请求；请求频率需要另行使用 debounce/throttle/cache/请求去重或框架数据层策略。

## 清晰度与生产决策

生产决策规则现在足够明确：能控制非紧急 `setState` 的触发位置时考虑 Transition；不能控制上游更新、只想让昂贵消费者滞后时考虑 deferred value；受控 input 保持 urgent；不要把调度 API 当请求层或计算消除工具。

## 建议修改

当前没有阻塞 Gate 的修改。后续如果要教学“被中断的 render attempt”，应单独设计可信 instrumentation，并明确 development Strict Mode、Profiler/日志本身对观测的影响，而不是从最终 DOM 值反推 React 内部尝试次数。
