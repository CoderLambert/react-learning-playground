## 事实与版本边界

React Router 当前区分 Declarative、Data、Framework 模式。普通用户导航应优先使用 `Link` / `NavLink`；`useNavigate` 用于程序式导航。Data / Framework 模式中，loader/action 数据流程内的跳转通常更适合 `redirect`。`replace` 替换当前 history entry，而 `navigate(delta)` / Back / Forward 在已有历史条目之间移动。

Pending navigation 不是 React Core 的通用 loading state；在 React Router Data / Framework 模式中可通过 `useNavigation` 等 Router API 读取。当前仓库没有安装 React Router，所以 Demo 不能声称验证 loader/pending/redirect runtime。

## Mental Model

本课应该先建立“导航 = location + history + route match 的状态转换”模型，再讨论 Router 模式附加的 data/pending 能力。这样学习者能解释为什么 push、replace、Back/Forward 的历史语义不同，也能理解 404 是 route matching 的边界，而不是组件内部的一个普通条件分支。

## Demo ↔ Note

当前 Demo 可真实执行：

- 打开 `/missing-page` 观察 unmatched route → Not Found boundary；

## 缺失边界 / 反例

建议后续真实接入 Router 时单独增加 pending-navigation lesson/experiment：slow loader、navigation location、局部 pending UI、redirect/error boundary，并区分 Declarative 模式与 Data/Framework 模式能力。

另外应提醒 `replace` 是产品语义决策：登录重定向、canonicalization 等场景可能适合替换，但普通可回退页面不应为了“少一条 history”随意 replace。

## 清晰度与工程决策

当前生产规则更清楚：能表达为真实链接的用户导航优先链接；程序式导航仅用于命令式流程；push / replace 按“用户是否应该回到上一 entry”决定；unmatched URL 必须有明确 route boundary。
