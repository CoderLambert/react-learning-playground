# Review: 具名多插槽与组件 API

## Verdict

本轮已修复原先的 Demo↔Note 三态契约不一致，并收窄了 Demo 对“工业级统一协议”和“零额外 DOM”的泛化表述。当前课程把三态明确限定为本项目的 API 设计选择。

## Hard gates

- **Gate A — Correctness: PASS**。具名 slot 由 props 传递可渲染内容的模型准确；当前文案不再声称 `false` 三态是所有成熟组件库的统一规范，也不再声称 slot 机制天然零 wrapper。
- **Gate B — Demo Contract: PASS**。Note、Demo 与 Source 现在统一使用 `undefined` = 默认、`false` = 显式隐藏、已提供内容 = 覆盖；Demo 的 default/custom/hidden 场景可以直接验证该协议。
- **Gate C — Mental Model: PASS**。学习者能够解释为什么 sentinel 是组件 API contract，而不是 React 自动赋予的语义。

## Important gaps / boundaries

1. React 本身允许 `null`、`undefined`、boolean 等值渲染为空，但这不代表组件 API 应同时公开多种“隐藏”写法。本项目选择 `false` 作为显式隐藏 sentinel，文档和实现必须持续一致。
2. 当前 JavaScript 实现仍会把 `null` 视为“已提供覆盖”，最终 React 视觉上渲染为空；这与 `false` 的协议分支不同。若未来迁移 TypeScript，建议用更明确的 slot 类型或 runtime contract 限制 API 表面。
3. 自定义 title/footer 路径会增加 wrapper `div`；只有 `false` 隐藏分支是不渲染对应区域，不能把“零额外 DOM”泛化为 slot 机制特征。

## Clarity / engineering usefulness

当前 Note 的价值集中在 API contract：先决定容器拥有的骨架、调用者可替换的区域，以及 default / override / hidden 如何编码。Demo 已把“三态协议”明确写成“本 Demo 的选择”，更适合作为工程设计范式，而不是虚构 React 标准。

## Recommended changes

- 若未来给组件加 TypeScript，优先把 `undefined` / `false` / override 的协议体现在类型和文档中，并决定是否接受 `null`。
- 保持“隐藏分支不渲染对应区域”的窄表述，不恢复“零额外 DOM 成本”这类绝对宣传。
- 最终 decision rule：**先定义 slot 的缺省、覆盖、隐藏语义，再写实现；不要让 truthy/falsy 判断偷偷成为 API。**
